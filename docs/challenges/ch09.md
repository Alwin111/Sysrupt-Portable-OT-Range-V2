# Challenge 09 — Trojan Historian

**Type:** Defensive · **Points:** 150 · **Surface:** Web (`/mail`, `/evidence`, `/investigate`) on TCP 80 · **Toolkit module:** none — plain `curl`

---

## The Story

A trojan tampered with the process historian (HIST-04): it quietly **deleted one sample** from the
`TURBINE.VIB` vibration trend to hide activity, classic anti-forensics. The live trend now has a gap.
The nightly backup still retains the deleted record, so the job is to find exactly which sample is
missing, read its value out of the backup, and **restore it** — then keep it stable long enough for
the historian to accept the correction.

The catch: the live trend also has **genuine comms-outage gaps** that the backup is missing too, so
the *first* gap you see is not necessarily the deleted record. You have to diff properly.

## What You Know

- Everything is on the badge's web surface at `10.0.1.1:80`.
- The IR webmail thread at `http://10.0.1.1/mail` points at a `TURBINE.VIB` trend gap and carries the
  backup as a **downloadable evidence attachment**.
- The attachment is served at `http://10.0.1.1/evidence?f=historian_backup` — it contains **two
  separate exports**: `1/2 LIVE TREND` (single tag) and `2/2 NIGHTLY BACKUP` (multiple tags, ordered
  by seq). Nothing is pre-joined and no gap is marked — you do the analysis.
- You restore via the **Record Findings** form at `http://10.0.1.1/investigate` (it POSTs to
  `/submit` with `ch=trojan`, `seq`, `value`).
- A correct restore must **hold stable for ~10 seconds** before the challenge latches solved. A wrong
  submit re-corrupts the record and resets that timer.

## Step 2: Filter the backup to the right tag and diff

<details>
<summary>Hint</summary>

The backup is a **multi-tag** export — `REACTOR.TEMP` and `PUMP.FLOW` are noise. Filter both exports
down to just `TURBINE.VIB`, pull out the sequence numbers, and compare them. You're looking for the
**one seq that is in the backup but missing from the live trend**.
</details>

<details>
<summary>Show command</summary>

```bash
# TURBINE.VIB sequence numbers in each export
grep '^TURBINE.VIB' hist.txt | awk -F, 'NR==FNR' >/dev/null   # (both sections are TURBINE.VIB-tagged)

# live-trend seqs (export 1) vs backup TURBINE.VIB seqs (export 2)
awk '/LIVE TREND/{s=1} /NIGHTLY BACKUP/{s=2}
     /^TURBINE.VIB/{split($0,a,","); if(s==1) print a[2] > "live_seq"; else print a[2] > "bkp_seq"}' hist.txt

sort -n live_seq ; echo "---" ; sort -n bkp_seq

# seqs present in the backup but absent from the live trend:
comm -13 <(sort live_seq) <(sort bkp_seq)
```

Live `TURBINE.VIB` seqs: `50 52 54 55 56 58` → gaps at **51, 53, 57**.
Backup `TURBINE.VIB` seqs: `50 52 53 54 55 56 58` → it has **53** but still lacks **51** and **57**.

So **seq 51 and 57 are decoys** (genuine comms outages, missing from both). The record the trojan
deleted is the one the backup still holds and the live trend doesn't: **seq 53**.
</details>

## Step 3: Read the deleted record's value

<details>
<summary>Hint</summary>

Now that you know it's seq 53, read that record's value straight out of the backup section — don't
interpolate or guess it from the neighbours.
</details>

<details>
<summary>Show command</summary>

```bash
grep '^TURBINE.VIB,53,' hist.txt      # -> TURBINE.VIB,53,742,Good
```

The deleted sample is **seq `53`, value `742`**.
</details>

## Step 4: Restore the record and hold it stable

<details>
<summary>Hint</summary>

Submit both the sequence number and the value together on the Record Findings form. After a correct
restore the page says "record restored — keep it stable ~N s more": that's the 10-second stability
hold. Leave it alone (don't re-submit wrong values) and it latches solved.
</details>

<details>
<summary>Show command</summary>

```bash
# restore the deleted record (seq 53, value 742)
curl -s -X POST http://10.0.1.1/submit \
     --data "ch=trojan&seq=53&value=742"

# wait out the ~10 s stability hold, then re-check / re-submit the SAME values to confirm
sleep 11
curl -s -X POST http://10.0.1.1/submit \
     --data "ch=trojan&seq=53&value=742"
```

The second response (after the hold) confirms completion and returns the flag:

```
wired{tr0jan_h1st_r3st0r3d}
```

</details>

Notes:
- Submit the **exact** backup value (`742`). Any wrong seq/value re-corrupts the record and **clears
  the stability timer**, so you'd start the 10 s over.
- The challenge marks solved once the correct record has been held for ~10 s — the first POST starts
  the hold, the second (after `sleep 11`) sees it latched and hands you the flag. Recorded completion
  then survives a reboot.

## What You Learned

- Deleted records show up as **gaps** in a trend, but not every gap is malicious — comms outages leave
  identical-looking holes, so you can't just grab the first missing sequence number.
- The reliable method is a **diff against a retained backup**: the deleted record is the seq that
  exists in the backup but not in the live trend, while gaps missing from *both* are benign outages.
- This is why offline/immutable backups matter for integrity recovery, and why anti-forensics
  (hiding activity by deleting data) is defeated by data you kept somewhere the attacker couldn't reach.
