# Challenge 03 — Trojan Historian

**Type:** Defensive · **Points:** 150 · **Surface:** Web (`/mail`, `/evidence`, `/investigate`) on TCP 80 · **Toolkit module:** None — plain `curl`

---

## The Story

HIST-04, the plant's process historian, has been compromised. A trojan deliberately deleted a sample from the `TURBINE.VIB` vibration trend to hide evidence of suspicious activity.

However, the nightly backup still contains the original data. The challenge is that genuine communication outages have also created missing samples, making it difficult to identify the malicious deletion.

Your mission is to investigate the incident, compare the live trend with the backup, recover the exact missing value, and restore the record through the investigation portal.

Be careful: the restored record must remain stable for approximately 10 seconds before the challenge is marked complete.

**Important:** Some missing records are caused by genuine communication outages. We must compare the live trend and backup instead of assuming every gap is malicious.

## Step 1: Access the Webmail and Retrieve the Evidence

<details>
<summary>Hint</summary>

Start by accessing the webmail portal. The IR email contains information about the compromised historian and the backup evidence attachment.
</details>

### 1.1 Identify the login endpoint

Initially, accessing `/mail` returned:

```text
HTTP/1.1 302 Found
Location: /
```

This means the portal redirected us to the login page because authentication was required.

We retrieved the login page HTML:

```bash
curl -i -L "http://10.0.1.1/evidence?f=historian_backup"
```

The HTML revealed the login form:

```html
<form class=card method=POST action=/login>
<input name=user>
<input name=pass type=password>
```

This tells us:
- Login endpoint: `/login`
- Username parameter: `user`
- Password parameter: `pass`

### 1.2 Login using curl

```bash
curl -i -c cookies.txt -X POST 'http://10.0.1.1/login' \
  -d 'user=eng&pass=Rec0ncile!42'
```

**What this command does:**

- `-i` displays HTTP response headers.
- `-c cookies.txt` saves the session cookies.
- `-X POST` sends a POST request.
- `-d` sends the login form data.
- Single quotes prevent Bash from interpreting the `!` character in the password.

### 1.3 Access the evidence attachment

After authentication, use the saved cookies:

```bash
curl -i -b cookies.txt \
  "http://10.0.1.1/evidence?f=historian_backup"
```

To save the evidence into a file:

```bash
curl -s -b cookies.txt \
  "http://10.0.1.1/evidence?f=historian_backup" \
  -o hist.txt

cat hist.txt
```

## Step 2: Compare the Live Trend and Nightly Backup

<details>
<summary>Hint</summary>

The backup contains multiple tags, so we need to compare only the `TURBINE.VIB` records.

We are looking for a sequence number that exists in the backup but is missing from the live trend.
</details>

### 2.1 Extract the sequence numbers

First, separate the live trend and backup sequence numbers:

```bash
awk '/LIVE TREND/{s=1} /NIGHTLY BACKUP/{s=2}
     /^TURBINE.VIB/{split($0,a,","); if(s==1) print a[2] > "live_seq"; else print a[2] > "bkp_seq"}' hist.txt
```

**What this command does:**

- `awk` reads the historian export line by line.
- When it finds `LIVE TREND`, it starts collecting live records.
- When it finds `NIGHTLY BACKUP`, it starts collecting backup records.
- `^TURBINE.VIB` selects only the vibration records.
- `split($0,a,",")` separates the CSV fields.
- `a[2]` extracts the sequence number.
- The sequence numbers are saved into separate files.

### 2.2 Display both sequence lists

```bash
sort -n live_seq
echo "---"
sort -n bkp_seq
```

<details>
<summary>Show result and explanation</summary>

**Live trend sequence numbers:**

```text
50
52
54
55
56
58
```

**Nightly backup sequence numbers:**

```text
50
52
53
54
55
56
58
```

Notice that sequence number `53` is present in the backup but missing from the live trend.

</details>

### 2.3 Find the missing record automatically

```bash
comm -13 <(sort live_seq) <(sort bkp_seq)
```

**What this command does:**

- `comm` compares two sorted files.
- `-13` hides lines unique to the first file and lines common to both.
- It displays only the lines present in the second file but missing from the first.

<details>
<summary>Show result and explanation</summary>

Actual output:

```text
53
```

This confirms that sequence number `53` exists in the nightly backup but is missing from the live trend.

**Why are the other missing sequence numbers not malicious?**

The live trend has gaps at:

```text
51, 53, 57
```

However, the backup also lacks `51` and `57`.

This means those two records were already missing from the backup, indicating genuine communication outages.

Sequence `53` is different because the backup still contains it.

Therefore:

**Deleted sequence number = 53**

</details>

## Step 3: Recover the Original Deleted Value

<details>
<summary>Hint</summary>

Now that we have identified sequence number `53`, retrieve its original measurement directly from the nightly backup.

Do not calculate or guess the value.
</details>

### 3.1 Search for sequence number 53

```bash
grep '^TURBINE.VIB,53,' hist.txt
```

**What this command does:**

- `grep` searches for matching text in the file.
- `^TURBINE.VIB` ensures the line starts with the correct tag.
- `,53,` selects sequence number 53.

<details>
<summary>Show result and explanation</summary>

Actual output:

```text
TURBINE.VIB,53,742,Good
```

We have recovered the original record.

| Field | Recovered value |
|---|---|
| Tag | TURBINE.VIB |
| Sequence number | 53 |
| Original value | 742 |
| Quality | Good |

**Deleted record:**

- Sequence number: `53`
- Value: `742`

</details>

## Step 4: Restore the Deleted Record

<details>
<summary>Hint</summary>

The challenge provides a Record Findings form at `/investigate`.

The form submits the following parameters to `/submit`:

- `ch=trojan`
- `seq` — missing sequence number
- `value` — original recorded value

We must submit the exact sequence number and value recovered from the backup.
</details>

### 4.1 Submit the recovered record

```bash
curl -i -b cookies.txt -c cookies.txt -X POST http://10.0.1.1/submit \
  --data 'ch=trojan&seq=53&value=742'
```

**What this command does:**

- `-i` displays the HTTP response.
- `-b cookies.txt` sends the authenticated session cookie.
- `-c cookies.txt` saves any updated cookies.
- `-X POST` submits the restoration request.
- `ch=trojan` selects the Trojan Historian challenge.
- `seq=53` identifies the missing record.
- `value=742` provides the original measurement.

### 4.2 Wait for the stability timer

After submitting the correct record, the challenge requires it to remain stable for approximately 10 seconds.

Run:

```bash
sleep 12
```

Do not submit any other values during this period.

### 4.3 Confirm the restoration

After waiting, submit the same values again:

Go to webpage and Submit 

or 

```bash
curl -i -b cookies.txt -c cookies.txt -X POST http://10.0.1.1/submit \
  --data 'ch=trojan&seq=53&value=742'
```

<details>
<summary>Show result and explanation</summary>

The challenge requires the restored record to remain stable for approximately 10 seconds.

The first correct submission starts the stability timer.

The second submission, after waiting, checks whether the restoration has remained stable long enough for the challenge to be completed.

**Important:** A wrong sequence number or value can re-corrupt the record and reset the timer.

The expected completion flag from the challenge description is:

```text
wired{tr0jan_h1st_r3st0r3d}
```

The actual flag should be recorded only after it is returned by the challenge server.

</details>

## What We Learned

1. **Historian data integrity:** Process historians store measurements collected from industrial equipment.

2. **Anti-forensics:** Attackers may delete historical records to hide suspicious activity.

3. **Backup comparison:** Comparing live data against a retained backup helps identify deleted records.

4. **Sequence numbers:** Sequence numbers help identify missing samples in a trend.

5. **False gaps:** Communication outages can also create missing samples, so not every gap indicates an attack.

6. **Data restoration:** Recovering the original value from a backup allows the missing record to be restored.

7. **Stability verification:** A successful restoration must remain stable long enough for the system to accept it.
