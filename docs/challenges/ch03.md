# Challenge 03 — OPC Scout

**Points:** 150 · **Difficulty:** Medium · **Surface:** OPC-UA-lite (TCP 9005)

> Spoiler-free. This guide explains the *surface* and the *idea* — not the answer.
> Note: this is a **custom OPC-UA-lite** service on port **9005** — not standard OPC-UA (not 4840) — so a
> real OPC-UA client won't speak to it. Connect to the service directly.

## The Story

Industrial servers expose their data as an **address space** — a browsable tree of nodes. Good recon
means walking that tree. But not every node is linked into it: some are reachable only if you already
know their id. Find the orphan.

## Where to start

- The OPC server listens on **TCP 9005**.
- The **monitoring email** (IR webmail at `http://10.0.1.1/mail`) points you at it.
- Start from the root and browse downward; look for a **Diagnostics** area.

## Objectives

1. Read the monitoring email.
2. Browse the address space from the root.
3. Use Diagnostics to discover an **orphan node id** (one not linked into the tree).
4. Read the orphaned node.

## Hints

<details><summary>1. I browsed everything and found nothing special.</summary>

A node can exist without being a child of anything you can browse to. Diagnostics/metadata areas often
leak the ids of such nodes even when the normal tree doesn't link them.
</details>

<details><summary>2. How do I read a node I can't browse to?</summary>

If you have the node id, you can read it directly — you don't need a browse path to it. That gap between
"browsable" and "readable" is the whole point.
</details>

## What you'll learn

- How an OPC-style address space is structured and browsed.
- Why "not linked" is not "not reachable."
- Why server diagnostics are an information-disclosure risk.

## Scoreboard

Awarded when the orphaned node is read.
