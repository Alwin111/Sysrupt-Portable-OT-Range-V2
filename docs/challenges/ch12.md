# Challenge 12 — Maintenance Override

**Points:** 300 · **Difficulty:** Expert · **Surface:** Modbus/TCP (TCP 502) · **Toolkit:** `sysrupt modbus`

> Spoiler-free. This guide explains the *surface* and the *idea* — not the answer.

## The Story

A critical setpoint is **write-protected**, and a reconciliation loop constantly rewrites it back to the
"correct" value. There is a maintenance window where writes *are* accepted — a timing game. Beat the
lock and the loop, and make your value **persist**.

## Where to start

- Same Modbus/TCP channel as #11 (port **502**); use `./bin/sysrupt help modbus` — note the
  **timing-sensitive** variants.
- Read the **engineering notice** (it explains the maintenance window).
- Expect a plain write to be **rejected** or **reverted** — that's the challenge, not a bug.

## Objectives

1. Read the engineering notice.
2. Observe a locked write being rejected / reconciled away.
3. Find the **unlock window**.
4. Write within it so the value **persists**.

## Hints

<details><summary>1. My write is accepted but then reverts.</summary>

A reconciliation loop is rewriting the register on a cycle. Writing once outside the window loses to the
loop. The window is when your write "sticks."</details>

<details><summary>2. How do I hit the window?</summary>

The notice describes when writes are honoured. The toolkit's timing engine exists for exactly this —
timing-sensitive commands let you place the write inside the short window instead of racing it blindly.
</details>

<details><summary>3. How do I know it persisted?</summary>

Read the register back after the loop has had a chance to reconcile. If it still holds your value, the
override took; the verification ladder reports the completion.
</details>

## What you'll learn

- How write-protection and reconciliation loops defend a setpoint.
- How maintenance windows become an attack opportunity.
- Timing-sensitive protocol interaction.

## Scoreboard

Awarded when the overridden value persists past the reconciliation loop.
